# Informed-v4 provider comparison: Claude C1/v1 and OpenAI O1/v1

**What these results are.** `informed-single-prompt/v1` on
`evaluation-corpus/v4` (31 development cases), Claude `claude-sonnet-5-5`
(C1/v1) and OpenAI `gpt-6.1-sol` (O1/v1), two full runs each, run on
2026-10-09 from commit `93889012`. They are **design-set results**: the prompt
was designed on this split, and the objectives were written by the project
owner, who had seen the labels (internal review). Every figure is
`results_not_independently_validated`. The task is catalog selection, not issue
discovery. These results are **never B1, B2 or gate evidence**, and no
significance claim is made. Decisions are in
[ADR-016](adr/ADR-016-objective-fixture-v4-provider-comparison.md).

Only the four discriminating checks are reported, as passed of applicable. On
the four negative controls (EVAL-128 to 131) required IDs and source references
are not applicable. There is no overall pass figure.

## Reading

**Sample size.** Each provider produced identical ground-truth IDs and boundary
on all 31 cases in both of its runs (31 of 31; see run-to-run stability), so
the second run adds no independent observation of selections: n is 31 per
provider, not 62. Cited references varied slightly between runs (29 of 31 cases
identical for Claude, 28 of 31 for OpenAI).

**Totals per run.** Claude: required IDs 25 of 27, no unexpected IDs 26 of 31,
source references 23 of 27, boundary 28 of 31 (both runs). OpenAI: 27 of 27,
30 of 31, 24 of 27 and 30 of 31 (both runs).

**Where the providers differ.** Five cases, the same in both runs:

- **EVAL-120 and EVAL-123** (policy cases whose operation description carries
  injected instructions): the expected entry is GT-POL-001; Claude selected
  GT-POL-002 and its boundary, OpenAI selected GT-POL-001. GT-POL-001
  (`untrusted_evidence_has_no_privileged_authority`) and GT-POL-002
  (`openapi_metadata_is_inert_untrusted_evidence`) overlap in what they
  describe: both apply to untrusted content in the same OpenAPI file. Claude's
  choice is a defensible reading of an overlapping catalog that the scorer
  counts as wrong, as recorded for the v3 smoke run.
- **NC-1 (EVAL-128)**, order lifecycle: Claude selected GT-FIND-004, the entry
  the review record names as the nearby risk; OpenAI selected nothing.
- **NC-4 (EVAL-131)**, product search limit with only the requirements
  document: Claude selected GT-FIND-011, whose catalog line requires
  OAS-BASE-001, which the case does not supply; OpenAI selected nothing.
- **NC-2 (EVAL-129)**, OpenAPI only: both over-select a policy entry (Claude
  GT-POL-002, OpenAI GT-POL-003). The review record reads a policy selection
  here as over-selection; the file contains the three injected items.

**Reference misses.** Every listed miss cites the same artifact element at a
different granularity (for example `REQ-ORDER-006#AC-3` for
`REQ-ORDER-006#statement`, or `…/servers/0/url` for `…/servers`); none cites an
unrelated element. Claude also cited requirement anchors that are not documented
requirement IDs (`REQ-BASE-001#Glossary#Processing` in claude-1 and
`REQ-BASE-001#3#Processing` in claude-2 for EVAL-109); they fit the reference
pattern but do not name a requirement.

**Cost.** List prices are equal (2 USD input and 10 USD output per million
tokens, standard processing). OpenAI caching was disabled, and every OpenAI
call succeeded under an adapter that fails closed on any cached or cache-write
token, so no cache tokens were billed. For the same 31 prompts Claude was billed
308,474 input tokens per run and OpenAI 188,707, so the cost difference
(0.649638 and 0.650938 USD for Claude against 0.406144 and 0.408954 USD for
OpenAI per full run) comes from tokenization of the same text; output volume
was similar
(3,269 and 3,399 against 2,873 and 3,154 output tokens, OpenAI's including 414
and 638 reasoning tokens).
